# 取り下げた・保留した検討

状態: 保留(取り下げた検討の要点。実装しない)

## 宣言的な画面の木への全面移行(取り下げ、2026-10)

GUI のすべての画面を宣言的な木(状態から作る値)にし、GUI(DOM)と TUI の両方が同じ木を描く、という案。詳しい設計(Elm 型、語彙、エクスプローラーの木、型案、移行の順序)を作ったが、現実的でないとして取り下げた。文書は削除した(コミット履歴に残る。`docs/core-plugins/` の `tree-model.md`・`vocabulary.md`・`explorer-tree.md`・`tree-types.md`・`migration-inventory.md`)。

維持するもの:

- core にデータと規則を置き、GUI と TUI がそれぞれ描く方式(`client-core` の `view`。[architecture.md](../design/architecture.md))。チャットの行(`view::Row`)・Markdown の木・補完・絵文字がこれ。
- 設定画面とナビゲーションバーの静的な木([ui-tree.md](../design/ui-tree.md))まで。

取り下げた理由として、検討で分かったこと:

- 木に載せる語彙が、画面を移すたびに増える。GUI だけに意味のある部分(サムネイル・ジェスチャー・アニメーション)を「GUI のヒント」にすると、TUI と共有できる部分が名ばかりになる。
- ブラウザー依存で、木の外(各 UI が描く)に残さざるを得ない部分が大きい: 入力欄(contenteditable・IME・貼り付け・選択範囲)、Lightbox のピンチ・ドラッグ、撮影(`video`)と画像の切り抜き(`canvas`)、通話の映像、PDF のサムネイル、ドロップ、ネイティブのピッカー、プラグインの DOM。
- ホストの状態(接続・ユーザー・メッセージ・既読・通話・設定)を木から読む仕組み(セレクターと効果)を作る必要があり、規模が大きい。
- チャットのタイムライン(`MessageList`・`MessageItem`)は、スクロールの張り付き・未読の区切り・ジャンプ・古い方の読み込みの組み合わせが複雑で、移行の回帰が大きい。

再開するなら、まず設定のサブページ(すでに木がある)とエクスプローラーで語彙を試す、という順序が検討されていた。
